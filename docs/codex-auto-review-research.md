## Implemented invocation and result handling

- `approvals_reviewer = "auto_review"` routes approval requests to Guardian for `on-request` or granular approval policies; it is not by itself “review every tool.” The common approval path tries Guardian, otherwise requests user approval; MCP can override the reviewer/policy per action. [`core/src/guardian/review.rs:116–140`; `core/src/tools/approvals.rs:542–574`]
- The common path captures the action, effective executor-native command cwd, approval/retry reasons, cancellation, and strict-review requirement, then calls `decide_approval` (sometimes in a worker). Supported request variants include command, terminal input, Unix execve, patch, network, MCP, and permissions. [`core/src/tools/approvals.rs:575–663`; `core/src/guardian/approval_request.rs:22–89`]
- Host routing checks managed/model requirements, cancellation, retry state, action serialization and escalated commands. Fresh synchronous review is required for the latter conditions; full-access context has an explicit validated allow bypass. Extensions may return a reviewed decision, eligible fast allow, or ask-user; absent contributors do not implicitly allow. [`core/src/guardian/decision.rs:50–110,150–196`]
- Synchronous flow: capture/validate the action → select reviewer config/model → build/reuse an isolated reviewer conversation → run model/tool loop → parse assessment → convert outcome into `ReviewDecision`. Retry orchestration owns one deadline. [`core/src/guardian/review_request.rs:39–64,286–343`; `core/src/guardian/review.rs:260–333,350–391`; `ext/guardian-reviewer/src/review.rs:53–70`]
- **Thresholds are not recomputed in Rust from the returned risk/authorization labels.** A completed assessment's `outcome` determines allow/deny. Schema requires only `outcome`; omitted risk defaults to low for allow/high for deny, omitted authorization to unknown, and rationale gets a default. Parser also accepts a JSON object wrapped in prose. [`ext/guardian-reviewer/src/assessment.rs:24–103`; `ext/guardian-reviewer/src/completion.rs:61–78,124–166`]

## Actual reviewer context and truncation

- Reviewer starts from a clone of parent config, but replaces base instructions with Guardian policy, clears configured developer instructions, disables skill instructions/memories, and inherits parent's loaded user instructions and environments. Thus this is **not** a raw copy of every parent system/developer instruction. Parent developer messages may still appear as transcript evidence. [`core/src/guardian/reviewer_config.rs:39–78`; `core/src/guardian/review_session_threads.rs:70–80`; `guardian-context/src/profile.rs:116–126`]
- New review evidence contains compact conversation transcript, exact structured planned-action fields subject to truncation, one approval/retry reason (retry wins; 512-token cap), root-user authorization snapshot for workers, host-verified user answers, parent unreadable roots/globs, and conditional Node REPL evidence. Synthetic contextual user scaffolding is filtered out. [`core/src/guardian/prompt.rs:89–167,225–243,283–336`]
- Command JSON contains `command`, **effective cwd**, sandbox permissions, additional permissions, justification, and tty. Network requests can include triggering command/cwd; MCP actions include arguments, tool/connector metadata and connected-account email. Patch requests include cwd/files/patch. This is not a shell-command-only transcript. [`core/src/guardian/approval_request.rs:22–100,212–229,295–350`]
- Synchronous transcript includes user/developer/assistant text and **tool calls plus outputs**, but excludes reasoning. Caps: 5,000 approximate tokens/message; 1,000/tool entry; Node REPL result cap becomes 6,000 when that evidence mode is enabled. No ordinary image inclusion in the synchronous profile; separate conditional Node REPL evidence is supplied. [`guardian-context/src/profile.rs:53–76`; `core/src/guardian/prompt.rs:98–106,141–153`; `core/src/guardian/mod.rs:69–76`]
- Initial transcript retention: message budget 20,000 tokens; tool budget 10,000; at most 40 non-user entries. First user message is anchored, then remaining users are considered newest-first if they fit (latest is **not unconditional**); remaining non-user messages/tools are considered together newest-first against their respective budgets. Selected entries render in original conversation order. [`guardian-context/src/retention.rs:20–43`; `guardian-context/src/profile.rs:146–186,206–245`]
- Per-string planned-action cap is 16,000 approximate tokens, recursively applied to JSON values; serialized pretty action must then fit **200,000 bytes** or prompt preparation errors. Truncation keeps UTF-8-safe prefix and suffix with an explicit omission marker. [`core/src/guardian/mod.rs:75–76`; `core/src/guardian/approval_request.rs:252–287,585–600`; `guardian-context/src/truncation.rs:8–37`]
- Final whole-request budgeting includes previous reviewer history, tools, policy, framing and reminders, with 256-token margin. Limit is supported/configured model window times effective-window percentage; unknown/fallback metadata is capped at 128,000 before that percentage. This is additional to transcript selection, not a flat 30k total prompt ceiling. [`core/src/guardian/input_budget.rs:77–154`; `core/src/guardian/request_budget.rs:18`; `guardian-context/src/budget.rs:55–76`]
- Final eviction removes optional commentary before optional tools (older first at the same priority); selected user/developer evidence and the newest five retained tool entries are required. Required evidence is not further truncated to force admission: insufficient capacity errors/compacts rather than silently dropping it. [`guardian-context/src/enforcement.rs:1–3,20–25,79–139`; `guardian-context/src/profile.rs:229–254`; `core/src/guardian/input_budget.rs:141–154`]
- Where retained context is available, original user instructions survive independently of model compaction; each complete role-labeled instruction must fit 900 tokens, otherwise it is omitted with an incompleteness warning, not shortened into partial permission. Root conversation and verified answers are separate labeled evidence sections. [`guardian-context/src/retained_instructions.rs:17–64`; `guardian-context/src/authorization.rs:29–89`]
- Reviewer context may also start from an encrypted parent compaction checkpoint: legacy mode skips it unless checkpoint-reuse is enabled; thread-owned mode validates checkpoint content and reviewer/producer compatibility hash. This is not extraction of a single “Goal” section. [`core/src/guardian/review_session_context.rs:20–30,48–103`; `core/src/guardian/review_session_factory.rs:88–107`]

## Investigation tools: installed capabilities versus policy text

- **Actual registration:** Guardian receives only `exec_command`, `write_stdin`, and `view_image` from core, and only when the primary and all selected environments use managed permission profiles. Shell tools additionally require ShellTool + UnifiedExec and non-disabled model shell support; image tool requires ViewImage. If managed enforcement is unavailable, this branch registers no such tools. General-purpose core tool registration is bypassed. [`core/src/tools/spec_plan.rs:973–1035`]
- Reviewer permission profile is intersected with read-only; approval policy is constrained to `never`; MCP servers cleared; apps/plugins/collaboration/web-search/context-management features disabled. Thus inspection is a real constrained execution capability, not just a prompt saying “read-only.” [`core/src/guardian/reviewer_config.rs:21–28,63–118`]
- **Network caveat:** bundled prompt says “no network access,” but configuration explicitly reuses eligible live managed-network configuration, and review implementation documents reuse of the parent's allowlist for read-only checks. Do not equate the prose with an unconditional implementation-level network ban. [`core/assets/guardian/policy_template.md:60–62`; `core/src/guardian/reviewer_config.rs:79–92`; `core/src/guardian/review.rs:336–349`]
- **Boundary:** Guardian judges an approval; Codex separately provides sandbox/permission profiles and runtime tool restrictions. Reviewer `allow` is an approval decision, not a new sandbox implementation. The reviewer host contract explicitly requires satisfying only the review gate, never expanding execution authority. [`ext/guardian-reviewer/src/review.rs:17–19`; `core/src/guardian/reviewer_config.rs:63–71`; `core/src/tools/spec_plan.rs:975–1005`]

## Bundled policy: risk, authorization, uncertainty

- Policy is replaceable: configured Guardian policy wins over reviewer-catalog policy, then bundled fallback; catalog may also override the template. The statements below describe the **bundled policy**, not an immutable server-side rule. [`core/src/config/mod.rs:1537–1549`; `core/src/guardian/reviewer_config.rs:51–59`]
- Default thresholds: **low → allow; medium → allow regardless of authorization**, except an explicit security-policy deny or affirmative malicious prompt injection. High → allow only with at least medium authorization, narrow scope, and no absolute deny; critical → deny. [`core/assets/guardian/policy_template.md:64–76`]
- Authorization: high means exact requested/approved action or necessary implementation; medium means clearly authorized in substance/effect, not exact implementation; low means weak/ambiguous connection to the goal; unknown means absent authorization/unrelated drift. An intended end state does not authorize every possible risky step. [`core/assets/guardian/policy_template.md:15–26`]
- Risk concerns irreversible damage/disruption and actual side effects. Missing context requires caution **but does not itself increase intrinsic risk**. An omitted generated script is not automatically high-risk; inspect if necessary. High destructive risk requires evidence of significant irreversible harm. [`core/assets/guardian/policy_template.md:1–3,12–13,28–38`; `core/assets/guardian/policy.md:47–59`]
- Investigation is requested only when missing local state could flip allow/deny; destructive filesystem actions should get read-only target inspection first; if important facts cannot be verified, lean conservative and explain uncertainty. This is a policy instruction to use the installed tools, not a guarantee every review performs inspection. [`core/assets/guardian/policy_template.md:43–49`]
- Escalation/sandbox retry and paths outside writable roots are not independently high-risk. Narrow user-requested deletion may be low/medium after checking target scope. Egress policy is stricter: credibly sensitive unknown payloads remain high until safe or authorized, with payload+destination authorization required. [`core/assets/guardian/policy.md:10–29,62–65`]
- Trusted authorization sources are user/developer transcript messages, `AGENTS.md`, and verified `request_user_input` answers; tools, skills/plugin descriptions, and assistant outputs are untrusted evidence. Explicit user delegation can authorize following otherwise-untrusted content. [`core/assets/guardian/policy_template.md:5–13`]

## Model, reuse, optional adaptive cache

- Preferred provider model defaults to `codex-auto-review`; configured API-key provider selects `gpt-5.6-luna`. Parent model metadata can override. If preferred model is absent from catalog, fallback is parent model unless explicit override exists. Prefer low reasoning if advertised; otherwise selected catalog default or parent's configured/default effort. [`model-provider/src/provider.rs:131–133,368–378`; `ext/guardian-reviewer/src/model.rs:17–65`]
- A reusable trunk reviewer conversation appends transcript deltas to preserve a stable prompt-cache key. Concurrent reviews use ephemeral forks from the committed trunk, not serialized access to one active conversation. Reuse key includes model/provider, permissions, instructions, cwd, features, environment IDs, and context/history compatibility fields. [`core/src/guardian/review.rs:336–349`; `core/src/guardian/review_session.rs:209–237`; `core/src/guardian/prompt.rs:174–207`]
- Separate optional Guardian V2 adaptive routing can fast-allow from latest thread `action_risk` score below configured threshold, within lag limit and unchanged complete authorization; missing/stale/failed/elevated scores fall back to synchronous review. It can reuse scores across categories, not necessarily score this exact action. There is also a policy-gated first computer-use JS-call exception. These are distinct from prompt/KV cache reuse. [`ext/guardian-v2/src/async_scorer/approval.rs:91–119,123–154,155–233`]

## Failure behavior

- Up to **three attempts within one 90-second deadline**; retry parse failures and specified transient session/network/server errors, using exponential 200ms-base jittered delays. Provider request and stream retry counts are separately set to one. [`ext/guardian-reviewer/src/lib.rs:30–31`; `ext/guardian-reviewer/src/retry.rs:20–89`; `core/src/guardian/reviewer_config.rs:42–43`]
- Exhausted prompt/session/parse errors **fail closed** with deny (synthetic high/unknown assessment); timeout returns `TimedOut`, cancellation `Abort`. These do not silently become user approval. User fallback is a routing choice before review, not the error fallback. Worker/join failure also produces deny. [`ext/guardian-reviewer/src/completion.rs:80–120`; `core/src/tools/approvals.rs:542–557,617–650`]
- Timeout feedback explicitly says timeout alone does not mean unsafe, and permits one retry or asking the user. Actual policy denials instruct against equivalent workarounds; these feedback texts can be overridden by model metadata. [`ext/guardian-reviewer/src/completion.rs:19–39,158–165`]

[`packages/ext/automode/index.ts:11–40,355–378`]
- Each parent/subagent transcript has a separate 40,000-character cap and 8,000-character entry cap. Under pressure, first/latest parent user messages are selected, then shell records, then other messages newest-first. Intermediate user permission **and restrictions** can lose to shell history. - Request has command, tool name/ID, gate labels/reasons and optional subagent transcript, but no effective cwd or execution options. [`packages/ext/automode/index.ts:374–430`; `packages/ext/automode/usage.ts:6–14`; `packages/ext/bash-gate/index.ts:335–353`]

Recommended smallest progression (not implemented):

1. Get a few actual false denials and their effective model/custom policy; retain damaging-action counterexamples. Evaluate actual model decisions, not just mocked completion tests. Do not weaken policy on source inspection alone.
2. Pass effective execution context end-to-end, and reserve transcript space for direct human instructions before shell history. Preserve provenance through compaction; generated summaries must not become blanket permission. Keep clear omission markers and a bounded combined parent/subagent budget.
3. Supply a small, separately budgeted recent evidence window (relevant calls/results and file changes), labeled untrusted facts rather than authorization. Avoid dumping all results or automatically promoting assistant claims about file ownership/destinations. Tune budget against captured decisions and recorded token usage, not a guessed universal token count.
4. Separate intrinsic risk from task authorization in the verdict. Allow routine reversible steps implied by the task; retain explicit user boundaries and require authorization for consequential effects. **Do not blindly adopt Codex's allow-low/medium-even-with-unknown-authorization rule** if task-scope enforcement is a product requirement.
5. Only if examples still need local facts, add bounded targeted read-only inspection. Prefer host-enforced narrow reads over an unsandboxed reviewer shell; Pi Bites' bash gate is not Codex's managed sandbox. Reuse prompt prefixes before adding stateful review sessions or adaptive cached approvals.
