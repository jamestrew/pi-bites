## Findings that change the earlier explanation

1. **Codex does not defer its standalone web tool by default.** `web::run` explicitly returns `ToolExposure::Direct` at both revisions. In CodeModeOnly that means its full documentation is included in `exec`. Deferring our `web_run` would adopt Codex's discovery mechanism with a different exposure policy. [Pinned web tool](https://github.com/openai/codex/blob/25af12f7e61572b0bc18ddb1008be543b91519b0/codex-rs/ext/web-search/src/tool.rs#L78), [checkout web tool](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/ext/web-search/src/tool.rs#L78).
2. **Native `ALL_TOOLS` can provide argument documentation.** Its entries contain only `name` and `description`, but Codex augments that description with a generated TypeScript declaration, including argument types/property documentation and supported return types. Saying it has no schema fields was structurally accurate but gave the wrong practical conclusion: the signature is inside the description text. This behavior already exists at our pin. [Pinned collection](https://github.com/openai/codex/blob/25af12f7e61572b0bc18ddb1008be543b91519b0/codex-rs/tools/src/code_mode.rs#L61), [pinned augmentation](https://github.com/openai/codex/blob/25af12f7e61572b0bc18ddb1008be543b91519b0/codex-rs/code-mode-protocol/src/description.rs#L355).
3. **Our current metadata differs here.** `nativeTools()` passes `definition.description`, while `execDescription()` separately prints `tool.section`, which contains the declaration. The standalone runtime's `ALL_TOOLS` uses the supplied description; it does not synthesize declarations from the schema. Consequently, removing the web section from `exec` alone would leave our metadata without its complete call signature. [Adapter contract assembly](../../packages/ext/codex-adapter/code-mode/contracts.ts), [adapter execute request](../../packages/ext/codex-adapter/code-mode/runtime.ts), [native global construction](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/code-mode-runtime/src/runtime/globals.rs#L70).

## Two cooperating discovery paths

### Nested Code Mode discovery

The native registry distinguishes runtime availability from initial prompt exposure. In CodeModeOnly, `Direct` tools that can be nested disappear from the top-level tool list and receive detailed sections inside `exec`. `Deferred` tools remain callable inside the runtime but their detailed sections are omitted from `exec`. The description adds guidance to filter `ALL_TOOLS` by name and description. Direct-only tools remain top-level. [Checkout registration](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/spec_plan.rs#L767), [description assembly](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/code-mode-protocol/src/description.rs#L261).

Every eligible nested definition, eager or deferred, is passed to the runtime. Runtime collection augments descriptions before producing `ALL_TOOLS`. A script can therefore print the relevant entries, read the returned documentation on the next inference, and then call the function. No separate tool registration is necessary for that nested call. [Checkout execution](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/code_mode/execute_handler.rs#L49), [definition collection](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/tools/src/code_mode.rs#L75), [metadata construction](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/code-mode-protocol/src/description.rs#L370).

For the proposed Pi policy, a discovery call could be:

```js
text(ALL_TOOLS.filter((tool) => tool.name === "web_run"));
```

This is documentation retrieval using a normal exec result, not an API `tool_search_output`. Returning all metadata indiscriminately defeats the token benefit. Discovery alone does not execute a web request or grant permission to run a tool.

### Native top-level tool search

Codex also advertises a special Responses `tool_search` tool when the model supports it, the provider supports namespaces, and discoverable deferred tools exist. This is a protocol tool, not an ordinary function with a magic name. Its client handler searches indexed tool metadata with BM25, defaults to eight results, validates a nonempty query/positive limit, and coalesces results into loadable namespace definitions. [Registration and gates](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/spec_plan.rs#L372), [model/provider gate](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/spec_plan.rs#L629), [search handler](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/handlers/tool_search.rs#L136), [search specification](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/handlers/tool_search_spec.rs#L16).

Search returns `ResponseInputItem::ToolSearchOutput` with `execution: "client"`, status, call ID, and structured tool definitions. It does not expand the original `exec` description. The search specification advertises source summaries unless the newer `DeferredToolWorldState` feature supplies that listing elsewhere. [Output conversion](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/context.rs#L194), [source-listing choice](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/spec_plan.rs#L1407).

Hosted search and client search both append discovered definitions at the conversation's end, preserving the preceding cached prefix. Loaded definitions still occupy context. Editing an earlier loaded tool set breaks caching from that point. The API documents this for GPT-5.4 and later; Codex's actual decision uses catalog/provider capabilities rather than inferring support solely from a name. [Official API tool-search guide](https://developers.openai.com/api/docs/guides/tools-tool-search).

The nested path similarly leaves the original tool definition stable and adds documentation as ordinary tool-result history. Preserving the prefix is a design inference from that message placement, not a guarantee of a cache hit on every provider/request. Discovery spends a model round trip; savings depend on which tools are subsequently needed and how long the conversation retains their documentation.

## What starts eagerly in Codex

There is no universal initial tool list for a model family: model metadata, enabled features, environments, provider capabilities, MCP configuration, and agent role contribute. The checkout catalog sets CodeModeOnly and search support for GPT-6 Astra and GPT-5.6 Sol/Terra/Luna. The older pinned catalog contains the GPT-5.6 entries but not Astra. The tool-mode resolver prefers model metadata and otherwise consults feature configuration. [Checkout catalog](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/models-manager/models.json), [pinned catalog](https://github.com/openai/codex/blob/25af12f7e61572b0bc18ddb1008be543b91519b0/codex-rs/models-manager/models.json), [mode resolver](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/mod.rs#L68).

The standalone web path requires namespaces, web support, an enabled web mode, and either Responses Lite or the standalone-web feature. Hosted web is considered when standalone web is unavailable and the provider supports web search; Responses Lite does not emit hosted tool specs. A short hosted tool selector on the wire should not be mistaken for evidence that the model has no web instructions. Our retained standalone client is the relevant comparison for `web_run`. ## Pin versus checkout

The essential deferred/eager split, BM25 tool search, declaration augmentation, and eager standalone web already exist at the selected runtime pin. A host upgrade is not required merely to retrieve deferred documentation through `ALL_TOOLS`. The checkout refactors registration, introduces more exposure combinations, caches immutable runtime definitions, optionally relocates source summaries to world state, and adds a provider web-capability check to standalone selection. Its execution path can discard explicit schemas after embedding declarations in metadata. These later implementation details should not silently become our contract source. [Pinned Code Mode planning](https://github.com/openai/codex/blob/25af12f7e61572b0bc18ddb1008be543b91519b0/codex-rs/core/src/tools/spec_plan.rs#L435), [checkout planning](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/core/src/tools/spec_plan.rs#L790), [checkout exposure types](https://github.com/openai/codex/blob/a62e98d18c6550e3bea152ed1b89d1e931dca961/codex-rs/tools/src/tool_executor.rs#L49).

## Proposed branch follow-up

For the current owned nested tools, use the native `ALL_TOOLS` discovery path: retain stable eager documentation for shell, polling, patch, and image; retain a concise web capability cue; omit the detailed web section from `exec`; supply the complete generated declaration-bearing description to runtime metadata. Keep web availability and every actual web execution subject to the existing route checks. This is a proposed local deferral policy, explicitly different from native web's eager policy.

Deferring the complete web section also defers its instructions about when browsing is required. Those instructions cannot help the model decide to discover the tool before it has read them. Retain sufficient initial browsing triggers or explicitly accept and document a changed browsing policy; a tool-name-only index would not preserve the current decision boundary. Measure discovery mistakes and extra round trips as well as token savings.

The initial prompt saves approximately the deferred web section minus the discovery cue; the earlier `/context` estimate for that section was about 2.13k tokens. This is an estimate, not tokenized provider usage. Once used, web documentation enters history. After compaction, discovery must remain available so missing documentation can be retrieved again. Saved discovery output restores documentation, not live capabilities or runtime state.

Top-level discovery for unrelated Pi tools is a separate integration question. It must use Pi's public dynamic-loading behavior and preserve tool execution ownership. Updating `exec`'s description after discovery would modify a base tool definition and undermine the stable-prefix objective. Do not infer a generic third-party executor from metadata, or expand the current five-tool dispatcher merely to support discovery.

### Stock Pi already supports top-level dynamic loading

The parallel Pi documentation/source investigation found an existing public path: register tools, initially activate a subset, then have a loader call `pi.setActiveTools()` with a purely additive set during tool execution. Pi records the added names on that result and exposes them for the next model request. The loader does not need to manufacture protocol references. Installed Pi 0.85.1 documents this in [extensions.md, Dynamic Tool Loading](/nix/store/1dp98a4mcph9wmb2jmc20h8qvjbnryys-pi-0.85.1/libexec/pi/docs/extensions.md#L2365).

Readable repository dependencies are Pi 0.85.0. Its [extension wrapper](../../node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/wrapper.js) captures `addedToolNames`; [deferred-tool conversion](../../node_modules/@earendil-works/pi-ai/dist/utils/deferred-tools.js) separates initial definitions from additions anchored in history. The stock [Responses conversion](../../node_modules/@earendil-works/pi-ai/dist/api/openai-responses-shared.js) emits `additional_tools` or completed client `tool_search_call`/`tool_search_output` items, depending on capabilities. [Responses](../../node_modules/@earendil-works/pi-ai/dist/api/openai-responses.js) and [Codex Responses](../../node_modules/@earendil-works/pi-ai/dist/api/openai-codex-responses.js) prefer `supportsAdditionalTools`, then `supportsToolSearch`, and keep immediate definitions in the request's initial tool list. The public compatibility declarations are in [types.d.ts](../../node_modules/@earendil-works/pi-ai/dist/types.d.ts).

This can support a normal Pi discovery tool for other registered top-level tools without replacing providers or authentication. It does not defer individual JavaScript functions embedded in one `exec` description: Pi sees `exec` as one tool. For our nested web function, the stable `ALL_TOOLS` path is the smaller applicable mechanism. Native top-level dynamic loading and nested documentation discovery can coexist, but their payloads and lifecycle behavior must be evaluated separately on actual configured routes.

A focused follow-up should verify actual initial and post-discovery provider payloads, full metadata declarations, conditional web availability, execution route rejection, model/session lifecycle changes, compaction and restored history. Compare input, cached input, output, and context use on real supported routes. Preserve the native runtime pin and existing authorization/rendering behavior; update the accepted contract records when implementing the exposure-policy change. No unit tests solely for prompt text are needed.
